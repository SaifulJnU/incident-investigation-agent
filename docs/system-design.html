Read-only by design. The worker searches and records. It cannot commit, push, restart, or roll back. Any future write would sit behind a human approval step.

1Request lifecycle

  1. Engineer opens a case for one service and clicks Investigate
  2. API checks the token and the service grant
  3. A second active run or a resolved case gets 409
  4. API queues a run and returns 202 immediately
  5. A worker claims it, skipping locked rows
  6. Searches are planned from the case brief
  7. Every enabled source runs in parallel
  8. Hits become evidence, gaps are named
  9. One model call writes the note
  10. The next poll shows it. A person marks the outcome

3Design decisions

Postgres is the queue

No Redis or SQS to run. SKIP LOCKED and a partial unique index rule out double runs.

Fan out first, then one model call

The model never loops on tools, so latency and cost stay flat and small local models work.

Crash recovery

A run stuck past RUN_TIMEOUT_MINUTES is failed and the case reopens.

Isolation by service

The token carries a service grant. Another service's case returns 404, so its existence stays hidden.

Swappable edges

Model and sources are environment settings. An unknown connector fails at startup.

4What you can measure

  • Time to a note: queued, running, completed or failed, with start and finish
  • Who acted: name and login for open, investigate, mitigate, resolve
  • Evidence: symptom, log, timeline, change, hypothesis, kept apart from the note
  • Outcomes: open, investigating, mitigated, resolved, counted on the case list
  • Tests: access, connectors, API and worker
