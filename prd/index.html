Product requirements for an investigation record any company can run.

One case record. Their model. Their tools.

Case file keeps an incident the same way for every company: what broke, the timeline, the evidence, and a note. The reasoning model and the systems it may search are plugs. A shop with a folder of logs and Ollama uses the same product as a shop with Bedrock, CloudWatch, and GitHub.

Worked example, Harbor and Co.

Harbor and Co. is a stand-in for any company. Their checkout API starts failing after a payments deploy. Nothing in this example calls Datadog or AWS. The log file shipped in this repository is the whole outside world.

Checkout errors after the payments deploy

checkout-api

Sev-1, open

Started 22 Sep 14:02 UTC. HTTP 500s on POST /checkout climbed after payments-api 1.42.0. Catalog still looks healthy. No database failover was announced.

The on-call engineer typed that. They did not type the cause.

The only tool that can search today reads examples/logs/checkout-api/api.log:

2026-09-22T14:02:11Z payments-api INFO deploy version=1.42.0
2026-09-22T14:02:40Z checkout-api ERROR upstream payments-api status=500 body="card vault timeout"
2026-09-22T14:03:02Z payments-api ERROR vault connection timed out host=vault.internal:8443

Those lines are not in the title. When a completed note mentions a card vault timeout, the model got that phrase from this file through search_logs.

What happens after Investigate

  1. The console asks the API to queue a run. The page does not wait on the model.
  2. The worker picks up the run and sends the whole case: title, service, severity, start time, and what happened.
  3. Strands calls Ollama llama3.1 locally, or Bedrock if that plug is selected.
  4. The model may call search_logs. That function reads the log directory and returns matching lines.
  5. The model may call record_evidence. That writes a timeline row, a hypothesis, or a log line onto the case.
  6. The worker stores the model’s final text as the incident note and the page shows it.

On the local llama3.1 run, step 4 happened and step 5 often does not. The model writes a sentence about calling record_evidence instead of calling it, so the timeline stays empty. The note can still be true. The timeline is empty because the tool did not run.

How the pieces sit

The browser never calls the model. The API never calls the model. Only the worker does, and only through the plugs that are switched on.

What a company turns on

Two companies install the same images. Each sets environment variables. Neither sees the other’s cases, because each has its own Postgres.

Plug Harbor and Co., local A production company
Model Ollama llama3.1 on the laptop Bedrock, or their own Ollama server
Logs Folder of text files CloudWatch, Datadog, or Loki, when that plugin exists
Deploys Not connected GitHub, when that plugin exists
Open a case A person, in the console Still a person. Slack or PagerDuty can be added later
Close a case A person marks mitigated, then resolved The same. The agent does not close it

Where this slice stops

Built: the case, the console, Postgres, the worker, Ollama, Bedrock, sign-in, service grants, and a log-folder tool. Not built: CloudWatch, Datadog, GitHub, and an approval step before any write to those systems. The agent is read-only toward company systems on purpose.
